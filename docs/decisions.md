# Decisions

Ambiguities resolved during the build. Newest last.

## 2026-09-28 Starting state
- The instructions say `prisma/schema.prisma`, `prisma/rls.sql` and `src/lib/tenant-db.ts` were already built and tested. The repository was empty (no commits, no remote branches). These three files are built from scratch in Phase 1, together with the isolation suite that proves them.
- The master spec section of the instructions contains only the five reference repository URLs. docs/master-spec.md saves it verbatim. Where the build phases refer to "every service in the master spec", "the full form template library" and "every node type in the master spec", the lists are defined here from the hero flows, the overrides and common school operations, and are recorded below as they are decided.
- `[DATE]` in the deadline is a placeholder. Treated as "as soon as possible"; the production URL must work at every checkpoint.

## cal.diy license
- The cloned cal.diy repo carries an MIT LICENSE, but CLAUDE.md groups it with the GPL/AGPL repos. CLAUDE.md wins, so nothing from cal.diy is copied; slot logic is reimplemented.

## Routing and locale
- Product routes live under `src/app/(app)/[locale]/...` (`/en/...`, `/ar/...`). The marketing site lives under `src/app/(marketing)` at `/` and `/demo`, with the locale read from a cookie and a toggle that sets it. Two root layouts, one per route group.

## Worker and retention
- The worker imports `src/server/queue-core.ts` and `src/server/demo/run-reset.ts`, which carry no `server-only` or Next.js request imports. `src/server/queue.ts` re-exports the queue core for the app. `runDemoReset` in the `"use server"` module is no longer exported, because every export of such a module is callable from the browser without the checks in `resetDemoAction`.
- `DeliveryStatus` has no in-flight state, so the worker claims an outbound row by moving it from `QUEUED` to `SENT` before calling the provider, then fills `sentAt` and `providerId`. Delivery is at most once: a crash between the claim and the provider call loses that message rather than sending it twice.
- One-off jobs (reminders, retention, `test.idempotent`) claim a `JobRun` row with `INSERT ... ON CONFLICT DO NOTHING` inside the same tenant transaction as their work, so a rollback frees the key for a retry.
- The sweeper's catch-up email for a lost `deliver` job has the subject and link but not the body, because the body is only carried in the job payload.
- Demo addresses use the reserved `.example` domain. The worker never sends to reserved domains and records them as `suppressed:reserved-domain`.
- Retention is conservative. DELETE is applied only to in-app notifications and AI drafts. Audit events are append-only for `app_user` (prisma/rls.sql), so the audit policy is counted and reported as `requires_owner`. REVIEW and ANONYMIZE policies never change records: eligible rows (closed requests and cases, and inactive students past the period) are counted into `lastRunCount` for a human to act on. Each run writes one `retention.sweep` AuditEvent with counts only.
- Automatic reminders for meetings linked to wellbeing or safeguarding cases go to the host only.

## People admin
- Staff are memberships that hold at least one staff role and are not linked to a student or guardian record. Adding a staff member creates the global User only when the email is new; an email that already belongs to this school is refused.
- `INVITED` means the account is prepared but sign-in stays off (auth only accepts `ACTIVE` memberships). An administrator activates it from the Staff tab. No email is sent; sign-in is through the school's SSO or a password set up by IT.
- Suspension is enforced in two places that already existed: `resolveActiveMembership` (password, OAuth and org switch) and `getCtx`, which rejects a non-active membership on every request, so an open session ends at the next page load.
- Guardrails: a member cannot suspend themselves or remove their own `school_admin` role, the last active `school_admin` can be neither suspended nor demoted, and only members with `school.manage` can grant, remove or suspend administrator access (a registrar with `people.manage` cannot escalate).
- CSV import validates in the browser for the preview and again on the server with the same module (`src/lib/people-csv.ts`). Grades are integers 1 to 13 (the schema stores `gradeLevel` as Int and has no KG levels). Dates accept `YYYY-MM-DD` or `DD/MM/YYYY`. Students upsert by `(orgId, studentNo)`, guardians match by email within the school, links are unique per guardian and student, and each row is its own transaction. Error entries hold only row number, field name and a code. Blank Arabic names fall back to English; blank identifiers never erase stored ones.

## Workflow builder
- The canvas always opens with an automatic top-to-bottom layout (src/server/workflows/layout.ts) and "Tidy layout" re-runs it. Saved positions are kept in the graph but are not relied on, and unsaved-change detection ignores positions.
- Validation (src/server/workflows/validate.ts) is one pure function used by the live Checks panel and again by the publish action. Loops are rejected because the engine runs each step once per request.
- Approval and condition steps must connect both exits (approved and rejected, yes and no). Seeded workflows all pass.
- A workflow counts as safeguarding when any SAFEGUARDING service uses it. It must open a SAFEGUARDING case assigned to role dsl, every approval, assign, task and meeting step must route to dsl, deputy_dsl or the case owner, and notify steps cannot target the student or guardians. The inspector only offers those choices, and validation enforces them on publish.
- Due dates and waits are edited in days in the UI and stored as hours (dueInHours, hours) as the engine expects.
- Adding a step while a step is selected inserts it after that step and relinks the path; with nothing selected it lands unconnected in the middle of the view.
- Draft with AI always loads the result as an unsaved draft. When no model is configured, a deterministic drafter builds a linear approval chain from English or Arabic keywords (parents, teacher, head of department, counselor, nurse, registrar, principal, IT, office, letter, meeting).
- Publishing appends WorkflowVersion n+1 and moves publishedVersionId; runs in progress keep their workflowVersionId. Linking workflows to services stays in the services admin.

## Hero flow E2E
- A parent or guardian who submits a request has given consent by submitting it. When an approval step resolves to guardians and one of them is the requester, the engine records that guardian's row as approved at submission (with a timeline event and an `approval.approved` AuditEvent, `meta.onSubmit`), instead of asking them to approve their own request. For a parallel-any step that settles the step; for sequential or parallel-all steps the other approvers still decide. This makes a parent-submitted subject change go straight to the teacher, then the Head of Computing, then the Registrar. It lives in the engine, so it applies to new requests without a demo reset; the seeded workflow graph did not need to change.
- When a family books a real slot before filling in a meeting form, the form's `withWhom`, `preferredDate` and `preferredTime` questions are hidden, because the booking already answers them.
- Booking a meeting from a case closes the workflow's open "book a meeting" task for that case.
- A parent sees a child's meeting on a wellbeing or safeguarding case (meetings list, meeting page, .ics, home widget, calendar) only when staff invited them to it. Meetings on standard cases, such as an academic referral meeting, show normally, including on the parent's calendar.
- The Playwright suite (`tests/e2e`, `playwright.config.ts`) creates its own requests and bookings on the demo school and never resets it, so it can run against a shared or production database. It signs in through `/demo` personas and runs every hero flow in English and Arabic.

## Subject registration and class allocation
- The registration window is a CalendarEvent of kind DEADLINE whose audience list carries the marker `registration_window` (plus student, parent and staff so it shows on everyone's calendar). Its start is the deadline (15:00 Dubai on the chosen day); the window is open while the deadline is in the future. Closing early moves the deadline to now. There is one window per school, the latest such event.
- The seeded window is open (deadline nine days out) so the student and parent flow can be shown straight away. After the deadline, students and parents see their choices read-only with a link to the Subject change request; staff with registration.manage can always register on behalf.
- Option blocks start at Grade 9, not 10, because Adam (Grade 9) already takes electives in the core seed. Blocks: A Physics, Computer Science, Geography; B Chemistry, Business Studies; C Economics, Biology, French; D Art and Design, Psychology. Physics and Computer Science share block A so the subject change demo is a clean swap.
- Prerequisites are subject codes. One is met when the student takes that subject in the same registration or took it in an earlier academic year. Seeded: Economics needs Mathematics; from Grade 11 Physics needs Mathematics and Biology needs Chemistry.
- Allocation (src/server/registration/allocate.ts) is a pure function per subject, grade and year. Existing placements are kept even over capacity; new placements go to the least full section with room (capacity default 24); when all are full it opens the next lettered section ("Grade 10 Computer Science B") with no teacher, for the timetable to fill. A student with a registration row for a subject but no active registration is removed from that subject's sections; enrollments without any registration row are left alone. Running it twice changes nothing.
- Removing a student from a class deletes the Enrollment row (existing pages do not filter by status).
- A completed subject_change request (update_status COMPLETED in the engine) marks the old subject DROPPED, registers the new one with source SUBJECT_CHANGE and allocates only that student.
- The subject sheet import is wide: student_no plus one column per subject (code, English or Arabic name), cells marked x, yes, 1, true or نعم. Core subjects are added automatically; each row must pick exactly one option per block. Unknown columns are listed and ignored.
- Seed: Grade 10 Mathematics runs as two sets (capacity 12, then allocation opens set B) so rosters show several sections and moving students.
- Grades: the gradebook is on /grades for every role. Teachers edit their own classes; a head of department edits and sees the classes of the department they head; the principal, school administrator and other view-all staff see every class read only (they hold grades.view_all, not grades.enter). Grade bands are edited on /grades?view=bands by staff with school.manage; everyone else sees them read only.
- Grades: "a term's grades are published" means the term has at least one published assessment for that student. Report cards only ever contain published grades, so a card generated by staff any time is still safe to show to the family and is stored with visibleToFamily. The PDF is rendered on download from a snapshot in the document version (storage key prefix reportcard:), so it needs no file storage.
- Grades: a per-grade comment is saved in the language the teacher is using (commentEn or commentAr) and families see it with the usual language fallback. The report card comment is the teacher's latest comment in that subject, or a short comment chosen from the average.
- Grades: publishing notifies each enrolled student and their guardians who receive updates once per assessment and student (in-app deduplicated by link, outbound by idempotency key grade:<assessment>:<student>). Unpublishing and publishing again never notifies twice.
- Grades seed: Adam is not enrolled in Computer Science in the core seed, so his strength shows in Maths and Physics (Computing would also be strong if he were enrolled); his weakest area is Arabic extended writing.
## Timetable, staff absence and cover
- The standard UAE day preset is 8 lessons of 45 minutes Monday to Thursday (assembly 07:30, breaks after lessons 3 and 6, end 14:35) and 5 lessons of 40 minutes on Friday with one break (end 11:25). 37 lesson periods fit a Grade 9 to 12 week of core subjects plus four option blocks; the preset dialog lets a school change every number.
- Periods per week come from SubjectOffering.periodsPerWeek (default 4). A section's option block is SchoolClass.optionBlock, or else its SubjectOffering's block for that grade. Sections of one grade and block run in parallel.
- Homeroom classes are not timetabled; registration happens in the assembly period.
- The demo seed only defines option blocks (PHYS/BUS/GEO, CHEM/CS/PSY, ECON/BIO, ART/FR) when neither the classes nor the subject offerings define them, and moves any student enrolled in two electives of the same block to a free block, so every student week is clash-free. When registration has already allocated students consistently this is a no-op.
- Regenerating keeps the row (and id) of every lesson that did not move, so cover already arranged stays linked. A moved lesson is locked automatically.
- StaffAbsence.reasonEn holds the notes for cover teachers (worksheets, instructions), which substitutes see. The form asks staff not to put private or medical details there.
- Cover declines are recorded as AuditEvents (`cover.decline`); a decliner is never picked again for that lesson. DECLINED means someone declined and nobody else was free; if someone else is free the cover goes to them and the reason stays visible on the board.
- Substitute ranking: people who already cover 3 or more lessons that week go last (fairness), then same department, then qualified for the subject, then anyone free; within a tier, under their weekly maximum first, then fewest covers this week and today, then lightest timetable.
- The head of the absent teacher's department gets the cover summary; when the absent teacher is the head or has no department, the principal does.
- Timetable lessons are a calendar kind that is off by default; cover is on by default.
## University pathways
- Accuracy first. Every starter programme is seeded `indicative = true`, `lastVerifiedAt = null`, because no university site (nor api.data.gov) was reachable from the build environment. Figures are typical published offers as generally known; anything not known with confidence is left out so the checker says "unknown" instead of guessing. Every requirement is shown with its official page link and "Not yet checked; confirm with the university" until a member with `pathways.manage` marks it checked. Editing a programme resets it to unchecked unless the editor ticks "I checked these requirements on the official page today".
- "Who checked it" and "who confirmed a grade" are stored as audit events (`pathways.program.verify`, `pathways.result.confirm`, `pathways.score.confirm`), because UniversityProgram, StudentSubjectResult and StudentTestScore have no confirmer columns. A result edited after its confirmation shows as awaiting confirmation again.
- University has no columns for SAT/ACT ranges or enrolment size. Those Scorecard facts are read from the snapshot file by `scorecardId`; name, city ("City, ST"), website and admission rate are stored on University. A `stats Json?` column on University would let the in-app import keep them too.
- ShortlistEntry has no programme id, so a shortlist entry is linked to its programme by university and English programme name. The shortlist card runs the checker live (met, not met, unknown and the gaps) rather than storing requirement rows that would go stale.
- Confirming results and scores is open to staff with `career.advise` or `pathways.manage` (counselors and career advisors). The admin page needs `pathways.manage` (career advisor, school admin), so the counselor persona confirms grades but does not edit programmes.
- Requirement subject codes reuse the school's Subject codes (MATH, PHYS...) plus FURTHER_MATH and ENG_LIT; a required subject the school does not teach is shown as "not offered at this school". Tawjihi and UAE MoE checks use the stream and average, not individual subjects.
- Parents can view the checker and enter grades and scores, but adding to a shortlist stays with the student and advising staff.
- Curriculum: a standard counts as "planned" when any lesson plan (draft, submitted, changes requested or approved) links to it; approved coverage is shown separately. Missing means no plan, "covered only once" means exactly one plan, covered means two or more. Coverage for a framework matches plans by the framework's subject and grade, optionally filtered to one class. Drafts are private to their author in lists, but still count in the aggregate coverage numbers.
- Curriculum: any member with `curriculum.plan` can plan for any subject and grade that has a framework (their own classes are listed first). This lets the demo teacher Daniel Carter, who teaches Physics 9 in the core seed, plan the Grade 9 Computing class the brief asks for. Plans are reviewed by the head of the subject's department; school leaders (`admin.access`) can review any subject. Nobody reviews their own plan.
- Curriculum: the "Grade 10 Science" demo framework is attached to Physics, since plans and frameworks are keyed by one subject. Standard statements are written generically in the style of the UK National Curriculum and UAE MoE outcomes, not copied from any document.
- Curriculum: document import reads PDF text with a small built-in extractor (Flate streams, object streams, ToUnicode maps), because no PDF parsing library is installed. Scanned PDFs have no text and the person is asked to paste instead. The deterministic fallback for both "curriculum_import" and "lesson_plan" works without an API key; AI output is never saved until a person accepts it, and accepted unit plans are always DRAFT with aiDrafted set.
- Curriculum: lesson plan bodies are bilingual. Activities and materials are JSON with en and ar fields; differentiation is stored as a JSON string {"en","ar"} in its text column. The editor edits one language at a time, and views fall back to the other language when a field is empty.

## Pathway engine (Sept 2026)
- One global university catalog shared by all schools: catalog tables have a nullable orgId. Null rows are global, readable by every school and written only by the owner role (seeds, worker, platform review). A school can add its own rows. This avoids copying thousands of programs into every tenant.
- Eligibility is computed only by the deterministic engine. AI may draft extractions (always reviewed, evidence must be a verbatim quote of the source) and narrative summaries; it never decides eligibility or picks courses.
- Requirement data that no person has checked against the official page is labeled Example (EXAMPLE confidence) in the UI. Nothing is presented as verified unless it is.
- API Ninjas is not used: it adds no requirement data beyond College Scorecard. Only COLLEGE_SCORECARD_API_KEY is read, from the environment.
- Search uses Postgres (ILIKE/trigram) instead of a separate search service for now.
- The demo hero student is Adam Nasser (Grade 9, American track), per CLAUDE.md, instead of the spec's Sharjah example.
## University application tracker
- The tracker grows the existing shortlist: "Start application" on a shortlist entry creates an Application (stage PREPARING), sets ShortlistEntry.programId when the programme is found, and keeps the entry's status in step with the stage. Applications can also start directly from a programme (server action), and without a programme (university only) when the shortlist entry has no matching programme.
- No schema change was allowed, so idempotency keys for generated tasks and letter requests live in JobRun ledger rows (queue "applications", name "task" or "letter", key `app:<application>:<item>:<intake year>:<role>`). The ledger row's result holds the task id, the date the generator last set, a date lock and an archive reason. A task whose date a person changed counts as locked; the counselor's due date field on an item locks it explicitly. Archived tasks are cancelled tasks with an archive reason in the ledger.
- Deadline precedence per kind: programme row, then university row, then route default; a school's own row beats a global catalog row at the same level. Route defaults only fill in when neither the programme nor the university lists a submission deadline, and are always labeled "Typical date, confirm with the university". Without a chosen decision plan the plan uses the earliest submission deadline still ahead (so US applications plan for 1 November until a counselor picks regular decision).
- Students move their own applications up to Submitted (and back while still preparing); after submission only staff change the stage, and interviews, offers, waitlists and rejections are always recorded by staff. Students tick checklist items off but cannot waive items or mark a recommendation letter done.
- Recommendation letters: the counselor assigns any active staff member; the teacher gets a Task linked to /career/applications/letters and a notification. Completing the task (letters page or the task list) marks the checklist item done. No letter content is stored, so students and parents only see who was asked and whether it was sent.
- Reminders: the daily worker job "applications.reminders" (07:45 Dubai) sends in-app reminders for application tasks overdue or due within 14 days to the task owner, and one daily digest per counselor. Parents get no digest: there is no school setting for it yet, so the brief's fallback (student and counselor only) applies.
- The calendar shows each open application's submission deadline (or nothing once submitted) as a "deadline" item for the student, their parents and the assigned counselor, reusing the existing deadline kind and filter.
- The board shows the coming intake (Grade 12 this year) and merges Researching into the Shortlisted column and Enrolled into Accepted, so eight columns fit a demo screen.
## Requirement data pipeline (catalog review)
- Platform access: global catalog rows can only be written by the owner role, so pipeline writes go through `src/server/platform/catalog-db.ts`, a lazily created PrismaClient on `PLATFORM_DATABASE_URL` (falling back to `MIGRATION_DATABASE_URL`). This is the "platform admin" exception to hard rule 2. Page reads still use ctx.db. Writing global rows needs `catalog.review` AND (the current organization is the demo school OR the member's email is in `PLATFORM_ADMIN_EMAILS`). Without an owner URL the review screens are read-only and every write control is disabled with a tooltip. Every publish, reject, verify, review, source add and check writes an AuditEvent in the reviewer's own organization.
- Pipeline rows take the orgId of the programme they describe: null for global programmes, the school's id for a school's own programme.
- The fetcher follows redirects by hand so each hop is checked against robots.txt; robots.txt answering 5xx is treated as "disallow everything", 4xx as "allow". Only HTML and plain text are accepted for now (PDF pages fail with `unsupported_type`). RequirementSource has no column for the final URL, so it is stored in the extraction's `normalizedJson.meta.finalUrl`. `SourceStatus.FETCHED` records the INSERTED outcome.
- Extraction in the worker is rule-based only: the AI provider module is `server-only` and needs a request context. AI extraction runs on demand from the review screen ("Extract again with AI", disabled with a tooltip without `ANTHROPIC_API_KEY`) through `generateAi` with feature `requirement_extract`. Model and rule output go through the same evidence validation. The cache key is (source, content hash, model, prompt version).
- Reviewer edits ("Edit and approve") may change a value away from its quote, but the quote must still be verbatim on the page; codes and ranges are checked again.
- Subject keys come from CanonicalSubject. The rule-based extractor finds phrases (for example "Further Maths") and maps them to whatever keys the catalog uses, by key or English name; with an empty catalog it uses a small built-in vocabulary. Levels: A-Level lines are ADVANCED, IB Higher Level lines are HIGHER.
- Publishing writes one version per curriculum group found on the page (general lines such as English tests go to the curriculum-null row); groups not on the page keep their current version. The first published version of a group records an informational change (WATCH, already acknowledged). Severity: new binding requirement or raised binding threshold MAJOR; lowered thresholds, weaker policies, new recommended subjects NOTABLE; source changes WATCH; when the source kind changes (for example mirror to official) every entry is capped at WATCH (collegedata rule). RequirementChange has no severity or Arabic summary columns, so both live in `diff` (`severity`, `summaryAr`, per-entry `summaryEn`/`summaryAr`).
- ChangeStatus has only NEEDS_REVIEW and ACKNOWLEDGED. "Mark reviewed" and "Dismiss" both set ACKNOWLEDGED and store `diff.review.outcome` (REVIEWED or DISMISSED). Only REVIEWED notifies. Recipients are active members whose roles hold `planner.approve`, `applications.manage` or `pathways.manage` in each school that has a student with the programme on a shortlist, in a course plan target or in an application. In-app only, idempotent per (change, recipient) through JobRun keys, with a bilingual MessageTemplate `catalog_requirement_change` created on first use. Students and parents are never notified automatically.
- The catalog seed from the engine uses sourceType `OFFICIAL_ADMISSIONS`; the pipeline treats it as `OFFICIAL_UNIVERSITY` (any `OFFICIAL_*` type counts as official).
- Demo requirement changes are told by adding the earlier state beneath the seeded current version (an older, closed EXAMPLE version plus the change), so current requirements and match results stay exactly as the catalog seed made them. Where a programme has no current version, an example base version is created and the change applied on top.
- College Scorecard: `University.stats` holds the extra fields with `source`, `dataYear` ("latest": the API's most recent release, it does not report the year) and `fetchedAt`. The catalog import needs `COLLEGE_SCORECARD_API_KEY` (no DEMO_KEY fallback) and writes to the global catalog; the older per-school import on the Manage programmes page is unchanged. Retries: 4 attempts, 300 ms doubling to at most 10 s, on 429, 5xx and network errors. Drift guard: the import stops before writing when an expected field is absent from every row of the first page.
## Pathway engine (global catalog, evaluation, plans)
- Global catalog: universities, programmes, intakes, curriculum courses and requirement rows live in the global catalog (orgId null), seeded by `seedGlobalCatalog` (prisma/seed/catalog) as the owner role on every deploy (scripts/docker-start.sh) and at the start of every demo seed. It reads everything once, compares in memory and writes only differences (about 0.4 s when unchanged, 1 s on an empty database). Schools no longer get per-org copies; the demo reset deletes the old copies with the rest of the tenant.
- Requirement data is EXAMPLE confidence. Values come from templates per field of study and university selectivity tier, with sourceUrl pointing at the university's official admissions page. Evidence quotes are left empty on purpose (a quote must be copied from the page, never invented); each row names where on the page to look. A seeded row is replaced by a new version only while it is still EXAMPLE; VERIFIED or REVIEWED rows are never overwritten by seed data.
- The legacy `UniversityProgram.requirements` JSON is generated from the same rows so the older /career/universities checker keeps working. Global rows are read-only for schools: the manage page labels them "Global catalog" and the edit, verify and university actions refuse them.
- Evaluation rules: status precedence is UNKNOWN_DATA > MISSING_REQUIREMENTS > NEEDS_MANUAL_REVIEW > POSSIBLY_ELIGIBLE > ON_TRACK > ELIGIBLE. A test not taken yet is "unknown, not taken" and keeps a student ON_TRACK (tests are taken late in Grade 11 or 12); every other unknown (grade not available, mapping that needs review, grade on another scale, EXTRACTED or UNKNOWN requirement row) gives POSSIBLY_ELIGIBLE. A curriculum with no row (when the programme has curriculum rows) gives NEEDS_MANUAL_REVIEW, as does a required NOTE. Interviews, statements, essays, references and portfolios are application steps and never gaps.
- SubjectRequirement.alternatives holds extra canonical subject keys (OR). SAT and ACT rows with the same policy in one row are alternatives. All language test lines in the applicable rows form one "any one of" group. TWO_OF counts a course once per group; a course may still satisfy lines in different groups.
- Grade profiles (A*AA, IB HL digits) use the student's A-level (ADVANCED) or IB HL courses, best grades first. IB points are computed from the six best IB grades when no total is recorded. Legacy StudentSubjectResult rows are read as courses only when no StudentCourse covers the same subject at the same level.
- "Classes that open the most doors" ranks against the student's record (not the plan) so it answers "what should I add"; courses start the year after the current one once that year has begun, and "required by" counts only lines not already met. Score = 100 per programme opened (to ON_TRACK or ELIGIBLE) + 20 per programme with fewer missing lines + 5 per programme that requires it + 1 per recommendation.
- Target programmes are chosen country by country (round robin in the goal's country order) so every chosen country is represented, best field weight and world rank first, up to 24.
- Prerequisites between standard courses (Algebra I before Algebra II, Precalculus before AP Calculus, IGCSE before A-level) are data in src/server/pathway-engine/prereqs.ts, keyed by global course code. Geometry and Algebra II may be taken in the same year.
- Plans: the current plan is the most recently changed DRAFT, PROPOSED or APPROVED plan. Any edit or regeneration returns it to DRAFT and clears approval; approving archives earlier approved plans. Students edit their own plan except while it waits for approval; parents view only; counselors and career advisors (planner.approve) approve or request changes (a note is required). Plan items that are not school catalog courses (for example a transferred IB student's subjects) are kept when the plan is edited.
- RequirementMatch rows are keyed by (student, programme, plan) and reused while inputsHash (engine version, profile, requirement row versions) is unchanged. CourseImpactAnalysis rows are replaced as a set when their hash changes.
## Transcript import, course record and counselor dashboard
- Matching order: exact course code in the row's curriculum, then normalized name (abbreviations such as Maths, Comp Sci, LNG & LIT expanded; Arabic letter variants folded), then bigram and token similarity on the subject words. Qualification words (IGCSE, A-Level, AS, AP, Honors, HL, SL), grade level, curriculum and "offered by the school" adjust the score. A row is matched automatically only at 0.8 or more AND at least 0.05 ahead of the next candidate AND in the row's own curriculum; otherwise it is NEEDS_REVIEW. Below 0.4 no course is suggested.
- Commit writes StudentCourse rows (source IMPORT, importId). Each import row remembers its StudentCourse id, so committing again updates the same rows. A course the student already has on record from another source (same catalog course and grade) is skipped and reported, never duplicated. Rows still needing review are saved as NEEDS_REVIEW (the engine treats them as unknown); "local course" rows are saved with no catalog course and CONFIRMED.
- The commit result (programmes whose status or missing count changed, and which rows newly meet a line) is stored in TranscriptImport.rows as `lastCommit`, because the table has no column for it. Import-level curriculum and reviewer decisions live in the same JSON (`{ v, curriculum, rows, lastCommit }`).
- XLSX is read by a small zip and sheet XML reader on node:zlib (first sheet, shared and inline strings, cached formula values); no spreadsheet library is installed. Old .xls files are refused with a message.
- Students may upload their own transcript and see its status; only staff with pathways.manage review and commit. On the course record students may change the predicted grade of courses that are not completed and suggest a mapping, which stays NEEDS_REVIEW until staff confirm. Parents do not see the course record (they see results on the pathway pages).
- Grades link: SchoolCourse.subjectId links a catalog course to a gradebook subject. The average uses published assessments of the current year only (the same figure the student sees). It is converted only for US letter grades (standard 97/93/90 cut-offs), percentages, and A-level and IGCSE letters through the school's grade bands; AP, IB and GCSE 9 to 1 show the average without a suggestion. The prediction is changed only when someone presses "Use".
- Dashboard: reads cached RequirementMatch rows (the current plan's rows when they exist, otherwise the record-only rows). "Required classes not in the plan" lists classes the plan-based evaluation still has to take, which means the plan covers them in no year (the cached results do not say which grade a planned course sits in). "Recompute" refreshes up to 60 students with a plan or a course record per click. The counselor filter uses CareerProfile.advisorId and Application.counselorId. ## Programme search and comparison (discovery)
- Search runs on Postgres: every word must appear in `searchText`, the programme name or the degree (ILIKE, AND across words). pg_trgm is not installed in the database, so there is no similarity ranking; the ILIKE path is what the brief allows and is fast at catalog size.
- The database filters text, field, degree type, level, teaching language, intake year and curriculum coverage; country (several at once), tuition band, match status and sorting run in memory on the programme metadata the engine already caches (a few hundred rows), then one page of 20 is shown.
- Tuition bands and the tuition sort use approximate US dollars (fixed rates in src/server/discovery/search.ts), because programmes charge in ten currencies. The programme's own currency is always what is displayed; the dollar figure is labeled "about".
- Match status: when it decides the order ("Best match", the default with a student) or the filter, every candidate is evaluated in memory with the pure engine; the chips on the visible page come from `computeMatches`, which reads and stores the cached RequirementMatch rows, so search and the hub agree. The plan in focus is the student's current plan, as on the hub.
- Staff can search without a student (no match status, "World rank" is the default sort) or pick any Grade 9 to 12 student. Parents see their child's status but cannot add to the shortlist (unchanged rule).
- Compare selection lives in session storage (a per-viewer convenience) so it survives paging and filtering; the compare page takes `?ids=` (2 to 4). Without a student the comparison uses a chosen curriculum (American by default, the hero track). Subject lines align by their set of canonical subject keys; a line naming several subjects aligns only with lines naming the same set. Rows where programmes differ are tinted. Deadlines use the applications deadline resolver for the student's intake year (Grade 12 intake without a student), with typical dates labeled.
- /career/universities no longer loads every programme: counts come from groupBy, filters run in the database, and the programmes tab is paged (24). The manage page pages programmes and universities (25) with a search and an All / This school / Global catalog switch. Both link to the new search.
- Global search (Ctrl K) adds up to 4 universities with programmes and 5 programmes for anyone with pathways.view. The catalog is not sensitive.

## Access management and joining (access module)
- Permissions are read from the database on every request (getCtx is cached per request only), so role and permission changes apply on the person's next click with no cache to invalidate.
- Sensitive permissions (safeguarding.*, cases.wellbeing, people.medical, people.reveal_ids, audit.view, roles.manage) need the role name typed to grant. The "Sensitive access" badge and the member warning ignore safeguarding.refer, which every staff role has and which reveals nothing.
- Audiences: only the built-in parent and student roles are family roles; school-made roles are staff roles. Family roles can only hold family permissions; staff roles cannot hold portal permissions (family.portal, student.portal, trips.consent, grades.view_own, registration.submit, career.use).
- Guardrail: at least one ACTIVE person must hold a role with roles.manage, and nobody can remove it from themselves. Checked for permission edits, restores, deletes, member changes and the existing staff edit dialog.
- Built-in role sync on deploy moved to src/server/identity/role-sync.ts and still skips customized roles. Restore default sets customized back to false.
- Staff invites create the person as an INVITED membership with roles and department right away (so they show in /admin/people), plus a personal link. The Invitation model has no department field, so this is where the CSV department lives.
- Looking up a token or join code before the person belongs to a school uses the owner client in src/server/platform/join-lookup.ts (the documented platform exception); everything after that is tenantDb/tenantTx. The web service therefore needs PLATFORM_DATABASE_URL or MIGRATION_DATABASE_URL; without it the join pages say joining is unavailable.
- Pending people (PENDING_APPROVAL) get a session that grants nothing: getCtx sends them to /join/waiting, their membership has no roles and no guardian links until approved, and the waiting page reads only their own request.
- No user enumeration: one CREDENTIALS error for every account problem. Creating an account with an email that already has a password works only with that password. A passwordless account the school created can take a first password only through a personal invite sent to that email.
- Rate limits (Redis, memory fallback): code lookups 30 per 10 minutes per IP, join submits 20, invite accepts 20, invite views 60, password attempts 10 per email and 50 per IP per 15 minutes. Five wrong child claims per hour per person or IP lock claims for that school.
- Parent approval off: every claimed child must match exactly (student number and date of birth, or grade and full name) to link straight away; anything else waits for approval. The same setting covers students joining with the code. Staff joining through an email domain with auto-approve start with the Teacher role.
- Emails to people who are not members yet go through src/server/notify/direct.ts (OutboundMessage with an idempotency key, delivered by the worker). Each email carries English and Arabic. If a delivery job is lost, the sweeper resends with the subject only.
- First-run tip cards show for 14 days after joining until dismissed (cookie per membership).
- The QR encoder is a small in-house byte-mode encoder (versions 1 to 10, level M), verified module for module against the segno library.

## Privacy tools (PDPL readiness) and pilot measures
- One-person export: /api/admin/privacy/export (compliance.manage) builds a ZIP in memory: summary.pdf (English and Arabic side by side), manifest.json, data.json, csv/<Area>.csv, files/ (stored uploads read through the storage abstraction) and withheld.csv. The person must be confirmed by typing their reference (student number, or the short id shown). Demo personas and the signed-in member cannot be erased. The User row (global) is anonymised only when the person has no membership at another school.
- DSR records gained guardianId and membershipId (staff); "Log request" creates one with a 30 day due date (a school default, not a legal claim).
- School exit export: one open export per school (QUEUED or RUNNING), built by the worker (queue "privacy", job "school.export", jobId school-export:<id>), claimed with a conditional status change and written to a fixed storage path, so a retry never builds twice. - Abuse protection matches /signup: a hidden honeypot field (a filled honeypot gets a fake success), 6 lead submissions per IP per hour and 3 per email per hour, 60 teaser scorings per IP per hour.
- ROI defaults (all labelled as assumptions on /pricing and editable there), chosen to be modest: 1 letter or certificate per student per year at 10 minutes saved; 0.5 absence reports per student per month at 3 minutes; 2 parent meetings per student per year at 6 minutes of booking back-and-forth saved; 1 parent message per student per month at 2 minutes; 10 school months; staff time at 60 AED per hour. For 600 students that is 57 hours a month. The page says it is an estimate, not a promise.
- Prices are never invented: per-student annual prices per module, pilot discount, pilot length and minimums (per school and per campus, pro rata for a pilot) are set by a platform admin on /platform/settings and only shown once published. A selection that includes an unpriced module, or no published prices (the default), shows "Request an offer", which creates an OFFER lead with the estimator inputs. Core services are always part of a plan.
- Referrals: each school gets an 8-character code (same alphabet as join codes) on first view of /admin/referral (school_admin or principal). /signup?ref=CODE shows "You were invited by ..." and records Organization.referredByOrgId at provisioning (email and Google/Microsoft sign-up). Unknown codes are ignored silently. No discounts are applied; the platform referrals page says commercial terms are agreed offline.
- Platform admin = email in PLATFORM_ADMIN_EMAILS. Pages live in the app shell under /platform (leads, referrals, settings) because platform admins are signed-in members of some school. In production an address on a reserved domain (the demo personas) is never a platform admin, since demo sign-in is public. Lead exports and pricing changes write an AuditEvent in the admin's school.
- Status (/status): live checks of the web app (the page itself), database (SELECT 1 as the app role), Redis (PING) and the worker (heartbeat key written every minute, fresh for 3 minutes). The worker records one UptimeSample per 5-minute slot (primary key = slot, so retries and replicas write once) and checks the web app through /api/health. A slot with no sample counts as down, because the worker or database could not record it; days before the first sample show "no data". Only up or down is shown, never hosts, versions or errors. Samples older than 100 days are deleted by the same job.

## Request conversations and private absences (Oct 2026)
- One thread per request in a new table (RequestMessage) rather than the case Message log, which records outbound email and texts. Visibility per message: SHARED ("Family and staff"), STAFF ("Staff only") and PRIVATE (author plus chosen staff, `privateToIds`). Families only ever query SHARED rows; the filter lives in one place (`visibleMessageWhere` in src/server/requests/conversation.ts) and is used by the page, the unread counts and the server action.
- Who is "the handling team": staff who can open the request through requestWhere (involved people plus requests.view_all holders; for wellbeing or safeguarding, the case permission). A staff member who asked for something (a leave request, a repair) is on the requester side: they see shared messages and private notes addressed to them, never the team's staff-only notes.
- Private notes are not visible to requests.view_all holders, the principal included. Private means private; the audit log records that a note was written (never its text).
- Requests linked to a WELLBEING or SAFEGUARDING case: staff need full case access (case-access.ts), every staff view writes `request.messages.view`, the family is never notified automatically, and "Notify the family now" requires a reason and records a ParentNotificationDecision (NOTIFY) on the case. On a request that is itself wellbeing or safeguarding (families only see "being handled"), the Family and staff option is disabled with a tooltip.
- Notifications for messages (in-app, email, push through notify with `reqmsg:<message id>` idempotency keys and the member's preferences, new kind request_message) never contain the message text: "Aisha Rahman sent you a message about ... Open Horizon to read it." Families: on a staff shared message. Staff: the assignee, earlier staff authors and pending approvers on a family reply (the office team when nobody has picked it up); chosen people for a private note; the assignee for a staff note.
- Sick days: absence reports now use a new workflow `absence_report`: illness and medical appointments go to the attendance office (registrar role), other planned absences to the principal. Approved days become EXCUSED attendance records with `source` (PARENT or STUDENT) and `requestId`; the homeroom teacher gets an in-app notice without the reason. The reason, details, doctor's note and the conversation are visible to the family, `attendance.reasons` holders (school administrator, registrar, school nurse) and `people.medical`; an approver sees a non-medical reason (the principal for a family trip) but never a medical one. Everyone else sees "Excused absence, reported by parent".
- The principal does not get attendance.reasons: leadership sees that a student is excused, not why. Schools can grant it per role on Roles.
- Staff absence: the old single notes field was always shown to substitutes as "Notes for cover teachers", so the migration renames it to `coverNotes`; the private reason is new (`reasonKind` plus optional `privateReason`). Private reason readers: the absent person, whoever reported it and `absence.reasons` holders (school administrator, principal). Cover managers without it (registrar, heads of department) see "Reason private". The substitute notice uses cover notes only (this fixes notifySubstitute sending the reason).
- An approved staff_leave request becomes a StaffAbsence (leave type as the private reason, the cover plan field renamed "Notes for cover" as cover notes) with cover arranged from today on; past days are left alone. The leave type and certificate are private like the absence reason.
- Form attachments (for example a doctor's note) are served by /api/requests/[id]/file with the same access as the page, only from the school's own storage prefix, and every opening (or refusal) is audited.
- Register: a read-only weekly register on each class page (marks come from the school's register or the SIS sync); the teacher home shows today's homeroom register card. Taking the register in Horizon is out of scope.

## Subject levels, AP guidance and elective impact (Oct 2026)
- A stored minimumLevel of ADVANCED is a coarse "school-leaving level" tag. For American lines it does not always mean AP, so each line is read from its verbatim quote (src/server/pathway-engine/level-guide.ts): AP required (the quote says AP, Advanced Placement, or names an AP-only course such as Calculus BC or Physics C), AP or a regular course (the same quote also offers a regular route: HS percentage, Calculus 12, Honors, dual enrolment), Senior-level course (Grade 12, Year 12, 11th grade or senior high school wording, no AP), Any level (no level stated). "AP required" is never given without AP in the quote.
- The engine evaluates American lines (and general rows for American students) against this reading, not the raw tag: AP required keeps ADVANCED; senior-level accepts a regular course from the stated grade or any AP course; AP-or-regular and any-level accept any course in the subject. Before this, a line such as McGill's "Pre-calculus" could never be met by an American student, because only AP courses are ADVANCED. ENGINE_VERSION moved to pe-3 so cached matches recompute.
- Calculus lines that name only Calculus BC (or say AB is not accepted) accept only AP Calculus BC; lines that accept AB also accept BC (the longer course). Other AP courses (for example AP Physics C, which carries some calculus) never meet an AP calculus line. The planner follows the same rule.
- Reviewed overrides (LEVEL_OVERRIDES, each with a reason): Manchester Business mathematics (grade B in a regular course; the three APs are a separate overall rule), Melbourne Science lab science (an AP exam), Khalifa University's five programmes (the row quote says the 80% is in Grade 12), University of Washington mathematics (a senior year quantitative course). Lines without a quote keep the stored level.
- Live catalog counts for the 94 current American subject lines: AP required 23, AP or a regular course 1, senior-level course 27, any level 43. The four general lines that mention AP (UAE University) are AP or a regular course. The official JSON files hold 97 American lines (three programmes are not in the catalog yet): 24, 1, 27, 45; a unit test pins these.
- Other curricula use their own level words from the stored level: British A Level, AS Level or GCSE; IB Higher Level or Standard Level; the existing level words elsewhere.
- AP exam rules written as notes on American rows (for example Imperial's "5, 5, 5 to include Calculus BC") stay notes for the engine (a person reads them), but the subject levels panel counts a course they name as included (Imperial: AP Calculus BC) as an AP requirement for that subject, with the quote.
- Targets are the student's university list (ShortlistEntry); without one, the first eight programmes matching the goal. Shortlist entries now store programId; older entries are matched on university and programme name.
- Elective impact compares eligibility with and without each option, with the engine: "Needed for N of your targets" and "Keeps N more programmes open" both count programmes where the option moves a required subject line from not met to met or pending (or fills one more slot of a two-of line), against the student's record plus their choices in the other blocks. The plan is left out on purpose, so a Grade 10 choice is not hidden by an AP course planned for Grade 12. The worldwide set is every programme with current requirement rows the school can see (311 in the demo). Results are cached in memory by input hash; the picker recomputes through a server action when choices change.
- The worldwide summary evaluates every one of those programmes against the record and current plan; "eligible or on track" are ELIGIBLE and ON_TRACK.
- Course selection for next year: when the school has an academic year after the current one with offerings, students and parents choose next year's grade (Grade 9 students choose Grade 10 courses) in their own window (a calendar deadline tagged with that year). Saving next year's choices never allocates classes. Staff switch years on /admin/registration. Offerings gained a track (curriculum; null means every track), the curriculum course they count as, and an AP flag; picking an AP course in the editor turns the flag on.
- Counselors and career advisors (pathways.manage or planner.approve) can open a student's course choices read only; only registration.manage can change them. Heads of department have neither, so they do not see the registration admin.
- Demo: next year's American offerings for Grades 10 to 12 with AP and regular versions in the same block, a few more students moved to the American track (students with no pathway records), most of whom have chosen; Adam has not chosen yet; Manchester, Birmingham, Toronto and UT Austin added to Adam's list so his targets range from AP Calculus BC only to regular courses.
- Subject pickers in service forms (for example a subject change) list the subjects taught this year (an offering or a class in the current year), so courses that only run next year do not appear; a school with no offerings or classes yet still sees every subject. Next year's American "Physics", "French" and "Economics" reuse the school's existing subjects of those names, so no two subjects share a name.

## Fees and invoicing (Oct 2026)
- Money is integer fils everywhere (database, services, exports as AED numbers with two decimals). Rounding is half away from zero, per line: pro rata, then discounts, then VAT on the line's net amount. Instalment amounts use cumulative shares, so a plan's parts always add up to the yearly fee exactly.
- VAT treatment is per fee item with defaults: tuition, registration, re-enrollment, seat deposit and books zero rated; transport, uniforms, trips, exam fees and other items standard rated at 5%. These are defaults only: **the school's accountant must confirm each item's VAT treatment** (the setup screen says so). A school that is not VAT registered issues plain invoices with no VAT. The VAT summary report shows totals by treatment for a period and does not claim to be the return itself.
- Tax invoices are never edited: a database trigger (Invoice_immutable) blocks changes to number, dates, parties, seller snapshot and totals; lines, credit notes and allocations are append only for the app role (prisma/rls.sql section 7). Corrections are credit notes (CN-), credited per line at the line's own VAT rate; crediting the rest of a line takes exactly the rest of its VAT. When a paid invoice is credited, the paid part is released (negative allocation rows) and becomes family credit.
- Gapless numbering: one counter row per school, document type and calendar year (Sequence key fees:INV:2026), incremented with INSERT ... ON CONFLICT DO UPDATE inside the transaction that writes the document. The row stays locked until commit and a rollback rolls the counter back, so numbers never skip or repeat under concurrency (tested with 12 parallel issues plus a rolled back one). Formats: INV-, PF-, CN-, RCT-, RF- plus year and five digits (prefixes configurable).
- Family accounts: one account per paying guardian (primary guardian link first), children billed together; a company sponsor can be the payer (legal name, TRN, address on the invoice). Sibling discount applies to tuition only, by position on the account, eldest child (highest grade, then date of birth) pays in full; default 2nd 5%, 3rd and later 10%.
- Discount stacking (documented in docs/guides/fees.md and tested): staff child, scholarship, bursary, other, sibling; percentages before fixed amounts within a kind; each on what is left; never below zero. Optional BEST_ONLY mode applies the single largest discount. Fixed awards are yearly amounts shared across instalments. Scholarships and bursaries always need approval by a second person (fees.refund.approve, four eyes enforced in the service).
- Early payment discount is not a line discount: it is a credit note (reason EARLY_PAYMENT) issued when a payment settles the whole invoice on or before due date minus N days. This keeps the original tax invoice intact and puts the discount in the VAT period it happens in. For online payment the link's creation time decides eligibility.
- Pro rata rules per school: whole months with a cutoff day (default 15th), days, or whole instalment. Lines store the units billed (prorataNum/Den) so a leaver credit is the unused part of each pro rata line. The school must check its regulator's refund rules; we do not encode any regulator's policy.
- Payments: "manual" provider (cash, card terminal, bank transfer with reference, cheque with number, bank and date). A cheque dated after the received date is HELD (post-dated): no receipt number and no allocation until it clears; a bounced cheque releases its allocations. Allocation is oldest due first unless an invoice is chosen; any excess is family credit (applied later or refunded). Payment forms send an idempotency key so a double submit records once.
- Refunds need a request (fees.collect) and an approval by a different person (fees.refund.approve), then a recorded payout with a refund number. Requested amounts are reserved against the payment so they cannot be refunded twice. Built-in roles: finance_officer (view, manage, collect, reports, no approval, so four eyes is natural), principal (view, reports, approve), school_admin (view). fees.refund.approve is not in SENSITIVE_PERMISSIONS (it guards money, not sensitive records); the second-person rule is enforced in the service.
- Billing runs are background jobs ("fees" queue): batches of 25 family accounts per transaction, a cursor on the run, and a unique (billingRunId, accountId) on invoices, so a retried or duplicated batch never bills twice and a stopped run resumes from its cursor. The worker re-queues runs with no progress for two minutes every five minutes. Without Redis the run is processed in the web process in the background. Progress is shown on the Billing page (auto refresh while running). A run can be stopped; invoices already issued stay.
- Online payments: PAYMENTS_PROVIDER selects one platform provider (console, stripe, ngenius, telr) and the school switches it on in Fee setup. Only adapters whose calls are fully implemented from public documentation report ready: console (built-in test checkout, HMAC-SHA256 signed events with the Stripe header scheme, secret PAYMENTS_TEST_SECRET or derived from AUTH_SECRET) and Stripe Checkout (session create, webhook signature t=,v1= with 5 minute tolerance, checkout.session.completed with payment_status paid). N-Genius (access token and order creation implemented from the public docs) and Telr (order.json create implemented) are **not ready**: payment confirmation (status call and webhook verification) is a documented TODO, so the app keeps showing "Online payment is not set up" with those providers. Per-school merchant credentials stored encrypted are the next step; today the provider is platform wide by environment.
- Webhook design: verify the signature on the raw body first; claim the provider event id in PaymentEvent (unique per school, provider, event); record the payment with idempotency key link:<link id> so two different events for one link still record once; the amount and currency must equal the link; a paid proforma becomes a tax invoice first. A failure returns 500 and rolls back the claim, so the provider retries.
- Reminders run daily (08:10 Dubai) and send only the latest stage reached (before due, then 7, 21, 45 days after by default), once per invoice and stage (JobRun claim plus notify idempotency keys), following each member's notification preferences (new kinds fee_invoice, fee_reminder, fee_receipt for parents, fee_approval for staff). Automated reminders are held for families with a child who has an open WELLBEING or SAFEGUARDING case; the check lives in case-access.ts (studentsWithAutomatedContactHeld) and returns ids only; finance screens never say why. Staff can send a reminder by hand. Families can be paused with a recorded reason.
- Finance hold is off by default and labelled "check your regulator's rules". When on, parents and students get a 423 page instead of the report card PDF if the family has an invoice overdue longer than the set days; the student's message does not mention fees. Staff always download.
- Parents see an account if they are its payer or are linked with parental responsibility (GuardianLink.canApprove) to a child on it. Students never see fees (no nav item, the fees page 404s, fee notification kinds are hidden from their settings).
- Reports are SQL aggregates inside tenant transactions (RLS applies), lists are paginated (25), and exports stream all rows for the period. Outstanding by grade shares each open invoice's balance over its lines in proportion to line totals. The accounting journal export uses plain ledger names (Accounts receivable, income by fee type, VAT output, Cash, Bank, Card clearing, Online payments clearing) for the school to map.
- Admissions: fees is the admissions seat booking provider. src/server/fees/admissions-link.ts calls registerSeatBookingProvider(feesSeatBookingProvider) and registers a seat paid hook that calls markSeatPaid; it is loaded at start-up by src/instrumentation.ts (web) and the worker, and admissions only uses it when FEES_SEAT_BOOKING is "on". Accepting an offer creates one proforma per application (sourceRef "seat:<application id>", idempotent) on an applicant family account in the admissions transaction, billed to the primary guardian as entered on the application; the reference is the proforma number. No online link is returned for applicants (they have no family login yet), so the family pays by the school's usual means and finance records it on the proforma. A payment that, with the family's existing credit, covers a proforma in full turns it into a tax invoice and is allocated to it; when a seat booking tax invoice is fully paid, markSeatPaid runs (it ignores a second call) and an admissions error never undoes the payment. createSeatBookingCharge(orgId, applicationRef, amountFils, payer) remains for callers outside a transaction and returns a payment URL for logged-in families when online payment is available. On this branch src/server/admissions/seat-booking.ts is a placeholder with the same exports; the main branch's version replaces it at merge.
- Data retention: invoices and receipts keep the bill-to name as issued (tax records). Erasure requests do not delete financial records; that interaction should be reviewed with the school's DPO before go-live.
- Demo: Horizon's fee schedule covers KG1 to Grade 12 (AED 16,500 to 29,500 a year; the demo school's own fictional figures), three zones, termly (default), monthly and annual plans, a fictional TRN, real billing runs for Term 1, the annual plan and monthly instalments already due, months of payments (spring re-enrollment, August and September collections), a returned cheque, four post-dated cheques for Term 2, early payment credit notes, a transport correction, a cancelled trip charge, a refund paid and one waiting for the principal, a pending bursary, a sponsor-paid family, a mid-term joiner billed pro rata, and an applicant seat booking. Term 2 is left unbilled so the finance officer can run it live. New persona: Farah Qasim, Finance Officer (enter-finance).
